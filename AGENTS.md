# Правила работы с проектом

- Во всём проекте каждую самостоятельную возможность оформлять в отдельном файле либо папке-модуле с одной ясной ответственностью: это относится к React/TypeScript, Rust, C++, скриптам и тестам. Не складывать новые функции разных областей в один растущий файл; существующие перегруженные файлы разделять при работе с ними. Небольшие вспомогательные функции держать рядом с той возможностью, которую они обслуживают; избегать раздробления на файлы-обёртки без пользы. После разделения проверять сборку, поведение и скорость работы.
- После завершённых изменений приложения повышать версию и собирать новый Windows EXE/установщик.
- Синхронизировать версии npm workspace, npm lockfile, Cargo и Tauri. Не перезаписывать старые версионные релизы.
- Перед передачей проверить успешность сборки и наличие артефакта; в итоговом ответе указывать версию и ссылку на новый EXE.
- Локальная сборка релиза разрешена. Публикация в интернете и установка на компьютер пользователя требуют отдельного указания.
- Все новые пользовательские тексты сразу добавлять в оба каталога `apps/desktop/src/i18n/ru.json` и `en.json` и выводить через i18n. Это включает меню, подсказки, aria-label, состояния, ошибки, подтверждения и системные сообщения. Не оставлять временные непереведённые строки.
- Русский — язык по умолчанию; выбранный язык сохраняется. Не переводить код, CAD-идентификаторы, имена файлов и пользовательские сообщения. Даты и числа форматировать с выбранной локалью. Для новых backend-ошибок добавлять перевод на границе отображения; технические подробности сохранять отдельно.
- Перед релизом запускать `npm run check:i18n` и проверять оба языка в интерфейсе.
- Новые элементы интерфейса должны поддерживать светлую и тёмную темы. Использовать тематические цвета поверхностей, текста и границ; WebGL-фон и сетка тоже следуют теме. Изменения оформления проверять в обеих темах, включая переключение без сброса сцены.
- Применённые SQL-миграции не менять: для изменений схемы добавлять новый файл. Файлы `apps/desktop/src-tauri/migrations/*.sql` сохранять с окончаниями LF на всех платформах и запускать `npm run check:migrations` перед релизом.
- После каждой реализованной функции, исправления поведения или изменения пользовательского сценария сразу обновлять подробную документацию на русском и английском. Описывать назначение, действия пользователя, технический маршрут, хранение данных, ограничения и проверку там, где это применимо. Поддерживать ссылки из README и индексов документации; не оставлять новую возможность описанной только в заметках о версии. После правок документации запускать `npm run check:docs`.

## Совместная работа людей и AI-агентов

- Порядок работы с двух ПК описан в [руководстве](docs/ru/collaboration.md). Перед началом читать этот файл, актуальный статус проекта и назначенную задачу GitHub; локальный handoff не заменяет общую задачу.
- Одна задача — один ответственный человек, одна ветка и явно указанные владельцы файлов. Сначала закрепить задачу в GitHub Issue, затем запускать агента. Другой агент не дублирует занятую задачу и не редактирует чужую область без согласования.
- Каждый человек работает в своём клоне; параллельные задачи на одном ПК используют отдельные worktree и ветки. Не переключать занятую ветку, не сбрасывать и не удалять чужие локальные изменения. Перед обновлением ветки проверять чистоту рабочего дерева.
- Изменения передавать небольшими коммитами и PR с описанием поведения, проверок и ограничений. Перед слиянием другой человек проверяет результат; ответственность за тесты не заменяется ответом AI.
- Один назначенный ответственный объединяет изменения, согласует номера миграций и зависимости, повышает версии, собирает и публикует релиз. Задачные агенты не меняют общие версии и не публикуют самостоятельно. Готовая задача передаётся ему для выполнения обязательного повышения версии и сборки.
- Не коммитить `.local`, личные handoff, базы и модели пользователей, журналы с личными данными, токены или ключи. Общие решения и следующие шаги записывать в Issue/PR либо согласованную документацию репозитория. GitHub не является автоматической блокировкой задач; назначение и освобождение задачи подтверждает человек.
