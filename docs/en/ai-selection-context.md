# Verified CAD selection in AI requests

[Documentation](index.md) · [Русский](../ru/ai-selection-context.md) · [AI](ai.md) · [Candidate review](ai-candidate-review.md)

Selecting a CAD face or edge can supply context for an assistant request. The host checks the selection against the current committed model before launching the external CLI. A viewport body ID, ordinal or semantic key is not accepted merely because it looks valid.

## User actions

Select a face or edge on the current revision and describe the desired change. A rejected or stale selection prevents the request from being sent: select again on the current model. If a legacy model has no supported CAD IR, a request without selection remains possible. The application does not silently remove invalid context and send a different request.

## Technical route

`plan_model` first checks revision and request shape. `agents/selection/trusted` then validates CAD IR v2, body membership, and SHA-256/size seals of the committed STEP and GLB. This applies to inline artifacts as well as stored files. Imported STEP inputs also pass their content-addressed asset checks.

The host enters the shared CAD queue with `selection_validation`, rechecks the committed head and artifacts after waiting, stages verified inputs in an application temporary workspace, and invokes the isolated selected-body worker. This queue is shared by projects within one application state; it does not provide a machine-wide permit across application processes. Its response protocol verifies fresh output checksums. `agents/selection/topology` reads bounded GLB metadata from that output, finds exactly one expected body, and checks the requested face/edge ordinal and the semantic key at that exact ordinal.

The saved preview and regenerated body must have identical face triangle counts, face areas and edge mapping (length, radius, sampled points, key and references when present). An unproved correspondence fails closed; there is no nearest-edge guess. The committed head, STEP/preview seals and imported assets are checked again immediately before transmission to the CLI.

An optional `topologyRef` uses the strict shared CAD IR schema: version 1, edge/face kind, owner feature ID, role and bounded occurrence path. It must equal the reference at the selected ordinal in fresh kernel output. Forging an owner or occurrence path, or supplying a face reference for an edge, is rejected. Sealed older previews without reference metadata remain compatible when their ordinal geometry mapping is identical; adding new metadata alone does not invalidate them. If an older preview already contains references, those must match too.

## Storage and limits

Validation creates no model revision, export or saved preview. Temporary output is removed by a scoped workspace; queue permits release on success, error or cancellation. The same cancellation token is used while waiting and executing. Selection remains revision-scoped context, not permission to modify the model and not a guarantee of a persistent topology identity. Candidate review and acceptance retain their independent checks.

Artifacts are limited to 40 MiB each and topology arrays to 100,000 entries. Only validated CAD IR v2 models with sealed STEP/GLB and matching native body metadata support this route. Legacy unnamed STEP previews and unsupported CAD IR require reselection after a supported rebuild, or a plain request. Exact mapping comparison deliberately rejects a preview regenerated by a different topology order or tessellation.

## Validation

Tests cover missing/duplicate or forged body IDs, stale revisions, invalid ordinals, keys belonging to another edge, swapped edge order, changed face mapping, malformed GLB lengths, source checksum/size tampering, and reference owner/path/kind tampering. Real-worker host tests check valid face and referenced edge selection, a forged reference owner, queue cancellation, changed head while waiting, and corrupted imported assets before process launch. Both inline and on-disk STEP/GLB corruption are rejected using an impossible executable, proving rejection precedes worker launch. The fixture follows the production artifact normalization route and appends imported-input changes as immutable revisions. All fixtures use isolated temporary data; they do not transmit requests to an authenticated provider or modify user projects. These tests verify the standalone host selection boundary; they do not prove rollback of the UI-dependent `apply_program` transaction or installed WebView behavior.
