# Полный запрос для AI друга

[Совместная работа](collaboration.md) · [Документация](index.md) · [English](../en/collaboration-ai-prompt.md)

У каждого человека отдельный клон FormaCAD и своя сессия AI. Сначала оба человека подтверждают, чей сейчас ход, закрепляют Issue и выбирают владельца релиза. Затем друг вставляет запрос ниже, заменив поля в угловых скобках. Чтение репозитория и локальная разработка не требуют доступа к личной переписке другого человека.

Аккаунт друга — **wenlixxq**, владелец репозитория — **lovlyDev**. Перед первой отправкой проверьте, что `wenlixxq` получил и принял приглашение с нужными правами: здесь его выдача не подтверждается. Запрос ниже рассчитан на подтверждённый ход друга; для обратного хода поменяйте владельца и проверяющего местами.

Запрос разрешает отправку **ветки назначенной задачи** после проверок, создание PR и обновление её Issue. Слияние проходит после проверки другим человеком; теги, релизы и установка имеют отдельные полномочия. Разрешение владельца текущего выпуска не выдаёт всем будущим сессиям бессрочное право публикации. Секреты и пользовательские модели в запрос не добавляют.

```text
Ты работаешь над FormaCAD — локальным AI-native CAD — в моём отдельном клоне.
Репозиторий: https://github.com/lovlyDev/FormaCAD
Сейчас мой подтверждённый ход: wenlixxq (передачу должен подтвердить lovlyDev).
Второй человек: lovlyDev; сейчас он только читает и проверяет, код не меняет.
Назначенная Issue: #<номер>.
Ветка задачи: task/<номер>-wenlixxq-<краткое-имя>.
Переданный исходный main SHA: <SHA>.
Мои файлы/модули: <явные пути>.
Чужие файлы и владельцы: <пути и имена>.
Согласованный API и зависимости: <контракт / ссылки на Issue>.
Цель и критерии приёмки этого хода: <конкретное поведение и проверки>.
Проверяющий человек: lovlyDev.
Ответственный за интеграцию версий, сборку и релиз: <имя / login>.
Разрешение на публикацию релиза в этом ходе: <не разрешена / отдельное явное поручение>.

1. Начни с чтения AGENTS.md, README.ru.md, docs/architecture-2.0.md, docs/ru/status.md,
docs/ru/collaboration.md, docs/ru/project-snapshots.md, docs/ru/architecture.md,
docs/ru/development.md, docs/ru/roadmap.md и назначенной Issue/последней передачи в PR.
Проверь фактические исходники затронутых модулей. Зафиксируй текущую ветку и SHA.
Если нет доступа к Issue, попроси владельца передать её текст без секретов;
продолжай независимое чтение исходников, но не выдумывай границы задачи или API.

2. Не предполагай, что на моём ПК есть чужие локальные файлы. Личные .local handoff,
протоколы сборки и память другого чата через GitHub не передаются. Общий полный
архитектурный план находится в docs/architecture-2.0.md и передаётся вместе с кодом:
его границы 2.0, последующие этапы 2.x и приёмка обязательны. Если этот файл или
уточнение исходного ТЗ недоступны, запроси подтверждённый текст у владельца до
зависимых решений. Краткий roadmap не заменяет полный master plan. Не заявляй
чужие проверки выполненными или недостающие функции готовыми.

3. Общая цель — завершить согласованную платформу Forma 2.0, а не просто менять
номера версий. 2.0 включает автономный локальный CAD без обязательного Python,
изолированный C++/OpenCascade worker, typed Command API/CAD IR для всех изменений,
проверяемые атомарные AI-планы и отмену/повтор, именованные тела/параметры/операции,
выбор CAD-граней/рёбер и честные границы ссылок, точные измерения/сечения, сравнение,
STEP/mesh обмен, Codex/Claude/Custom CLI, понятный согласованный интерфейс,
русский/английский и обе темы. Переносимая папка должна стать настоящим источником
истины проекта, а общий индекс — списком недавних проектов/настроек. Нужны единые
backend/location/session/epoch для всех потребителей, OS lease, режим чтения и
проверенная копия, явное восстановление, резервные копии/миграции, безопасное
пропадание носителя, полный/redacted cadpack и корректная передача проектов.
Формат хранения выбирается по реальным замерам и восстановлению, не по названию БД.
Для настоящих старых проектов 1.1 создаётся НОВЫЙ проект из последнего STEP;
не обещай восстановление старых операций/истории и не меняй старые данные тихо.
Windows приоритетен; полная приёмка 2.0 требует macOS arm64/x64 и Linux, bundled CAD,
работы offline, установленного приложения, крашей/отмены/повреждений/доступа с двух
процессов и проверки экспортов. WebGPU должен иметь рабочий WebGL2 fallback.
Будущие полные эскизы/сборки/чертежи/Lua/WASM/производство/симуляция — отдельные
этапы 2.x; не выдавай их за уже реализованное и не создавай пустые панели обещаний.
Эта сводка не отменяет утверждённое исходное ТЗ и не доказывает готовность 2.0.

4. Работаем по очереди. Не начинай запись до подтверждения моего хода и назначения
Issue. Проверь git status --short ДО fetch/pull и переключения ветки. Сохрани все
локальные файлы; незнакомые изменения не перезаписывай. Для чистого клона получи
origin/main, обнови main через pull --ff-only, сверь SHA с передачей и создай ветку
задачи. При расхождении останови зависимую запись и объясни конфликт; не применяй
reset --hard, git clean, force push, переписывание чужой истории или Git GC ради
удаления чужих следов. Если передана незавершённая ветка PR, продолжай именно её
по подтверждённой передаче, а не называй её код уже объединённым main.

5. Реализуй назначенную задачу полностью в пределах моих модулей. Каждая отдельная
возможность — ясный модуль/файл. Согласуй изменения общих i18n, lockfile, миграций,
IPC и версий с их владельцем. Применённые миграции не редактируй; новые — LF.
Обновляй RU/EN тексты и тематическую документацию сразу; сохраняй обе темы,
состояние сцены и совместимость данных. Не подменяй тест реального выбора/worker
setters, ослабленными assertions или утверждениями по одному UUID.
Если используешь субагентов, назначай им непересекающиеся файлы и проверяй результат;
это не передаёт ход второму ПК. Не запускай конкурирующие тяжёлые native сборки.

6. Выполни проверки по изменениям и правилам проекта. Перед сдачей проверь
check:docs, check:i18n, check:migrations, check:version; frontend/Rust/C++ и реальные
browser/native сценарии выбирай по затронутому маршруту. Проверяй ошибки, отмену,
stale/recovery и данные, когда они затронуты. Описывай реальные команды/результаты,
пропуски и ограничения. Не называй mocked browser установленным WebView, local SSD
тестом NAS, read-only capture полной внешней authority или source build готовым EXE.

7. После проверок я разрешаю тебе сделать небольшие коммиты только назначенных
файлов, отправить ветку этой задачи в origin, создать PR с Issue и обновить Issue
сводкой. Перед git add проверяй diff и добавляй явные пути. Не отправляй .local,
личные handoff, пользовательские базы/CAD-файлы, токены, ключи и сборочные кеши.
Не отправляй прямо в main. Не объединяй PR до подтверждённого ревью другим человеком.
Не создавай тег/релиз и не устанавливай приложение без отдельного явного поручения.
Если я назначил тебя интегратором этого хода, после принятия изменений синхронизируй
npm/workspace/lockfile/Cargo/Tauri версии, собери НОВЫЙ Windows EXE и проверь наличие,
версию, hash/состав и нужные сценарии. Сохрани прежние релизы согласно AGENTS.md.
Публикация этого проверенного выпуска требует отдельного разрешения выше.

8. Итог: Issue, ветка, commit SHA, изменённые файлы, API, проверки, ограничения,
ссылка на PR; версия и ссылка на новый EXE, если ты назначенный интегратор.
Напиши, что реально закончено в этой задаче и что осталось до полной приёмки 2.0.
Подготовь передачу второму человеку: merged main SHA (либо явно unmerged PR branch),
следующая Issue/границы/владелец и ответственный за релиз. Ход передают люди:
после подтверждения передачи прекрати редактирование до следующего назначенного хода.
```

Команды подключения и получения кода приведены в [основном руководстве](collaboration.md); полное общее ТЗ — в [архитектурном плане](../architecture-2.0.md). Запрос не подтверждает автоматически назначение человека, наличие секретов подписи, готовность установки или результаты тестов на другом ПК. Проверяйте текущий [статус](status.md), а не зафиксированный номер версии в старом чате.
