# Совместная работа с двух ПК и AI-ассистентами

[Документация](index.md) · [English](../en/collaboration.md) · [Состояние проекта](status.md)

Два человека могут разрабатывать Forma с двух ПК, каждый со своей сессией ChatGPT/Codex. Через GitHub передаются исходники, назначения задач и результаты проверки. У каждого должен быть отдельный локальный клон, своя учётная запись GitHub и доступ к репозиторию. Одна сессия не видит незакоммиченные файлы и личную переписку другой: ей нужно читать репозиторий и назначенную Issue.

Это порядок разработки, а не одновременного редактирования CAD-проекта. Базы приложения, личные модели и секреты не хранятся в Git. Для переноса модели используйте проверяемый маршрут приложения из [руководства по проектам](projects.md). Эти инструкции не заявляют готовность всей версии 2.0 и не настраивают защиту веток автоматически.

## Рекомендуемый режим: по очереди

Для этой команды владелец репозитория — **lovlyDev**, аккаунт друга — **wenlixxq**. Эти имена определяют участников передачи; наличие приглашения и прав записи нужно проверить отдельно. Руководство не утверждает, что доступ уже выдан. Приёмку и решение о слиянии выполняет глава проекта lovlyDev независимо от того, кто реализовал задачу. Проверка вторым участником необязательна; текущий владелец хода и релиза назначается явно.

Оба человека могут получать и отправлять изменения, но право изменять код передаётся явно: сначала человек А, затем человек Б. Пока А работает, Б может читать и проверять результат, но не начинает другую запись в общий код. Субагенты активного человека допустимы внутри закреплённой задачи с раздельными файлами; второй ПК не получает право записи автоматически. GitHub не реализует эту очередь сам: люди подтверждают передачу в Issue или своём согласованном канале.

1. А закрепляет Issue, ветку и пути, записывает исходный SHA. Б подтверждает, что сейчас только читает/проверяет.
2. А выполняет задачу, проверяет diff и нужные тесты, отправляет небольшие коммиты своей ветки и открывает PR. Полномочие отправки относится к согласованной задаче; публикация релиза назначается отдельно.
3. Глава проекта lovlyDev проверяет PR и принимает решение о слиянии. Если нужны исправления, А остаётся владельцем хода. После согласованной проверки назначенный интегратор объединяет PR. Непроверенные изменения не передаются как готовый `main`.
4. А сообщает: «Ход передан Б; Issue #…, PR … объединён; main SHA …; проверки …; ограничения …; следующий объём …; за версии/релиз отвечает …». А прекращает редактирование до следующего подтверждённого хода. Публикация ветки без передачи не освобождает задачу.
5. Б подтверждает передачу, проверяет чистоту своего клона, получает актуальный `main` и создаёт новую ветку своей Issue. После его PR, приёмки главой проекта и передачи хода разработка возвращается А.

Перед получением изменений на каждом ПК проверьте рабочее дерево **до** fetch/pull. При незакоммиченных правках не переключайте ветку и не подтягивайте изменения поверх них: сначала сохраните работу с её владельцем. Для чистого дерева и подтверждённого хода:

```powershell
git status --short
git fetch origin
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git switch -c task/456-friend-next-step
```

Сверьте SHA с передачей. `pull --ff-only` при расхождении остановится: не заменяйте его reset/force; согласуйте расхождение. Если PR не объединён, явно передавайте именно его ветку и SHA, а не называйте их `main`. В этом варианте подтвердите нового владельца той же задачи и обычное продолжение ветки; не запускайте параллельно второго автора и не переписывайте опубликованную историю.

На каждом ходе назначайте одного интегратора версий/релиза. Завершённые изменения приложения требуют согласованного повышения версий и нового проверенного Windows EXE по AGENTS.md. Полная 2.0 объявляется только после всей приёмки из [общего архитектурного плана](../architecture-2.0.md), а публикация разрешена лишь назначенному владельцу выпуска. Готовый [полный запрос для AI друга](collaboration-ai-prompt.md) включает эти границы и список источников. Личная память чата и `.local` не передаются через pull.

## Закрепите задачу до запуска агента

На каждую независимо проверяемую задачу создайте GitHub Issue. Назначьте одного ответственного человека и укажите ветку, исходный коммит, разрешённые файлы/модули, ожидаемое поведение, исключения и проверки приёмки. Комментарий «Взяла Анна; ветка task/123-anna-section-ui; мои файлы — управление сечением и тесты; backend у Бориса» делает границы видимыми. Второй человек проверяет открытые Issues и PR, прежде чем брать другую задачу.

Назначение Issue — запись договорённости людей, а не атомарная распределённая блокировка. Если задачу одновременно взяли двое, сначала выберите одного владельца. Разделяйте работу по ясным модулям: один агент может делать интерфейс, другой — Rust, но контракт API и владельцев общих файлов согласуйте заранее. У общих каталогов i18n, lockfile, номеров миграций, версий и метаданных релиза должен быть назначенный владелец. Передавайте ему нужные изменения вместо одновременного редактирования.

При создании Issue используйте [форму задачи разработки](../../.github/ISSUE_TEMPLATE/development-task.yml) репозитория. Она собирает ответственного человека, ветку/основу, свои пути, исключения, API, критерии приёмки, проверяющего, владельца релиза и передачу. Форма не назначает аккаунт автоматически: укажите человека в поле Assignees GitHub и подтвердите закрепление. Для обычного текстового описания используйте шаблон, значения замените своими:

```text
Ответственный: Анна
Задача / ветка: #123 / task/123-anna-section-ui
Основа: <SHA коммита>
Цель и приёмка: <наблюдаемое поведение и проверки>
Мои файлы/модули: <пути>
Зависимости и API: <связанная Issue, согласованный контракт>
Вне задачи: <чужие модули, версии, релизы>
Состояние: взята / работа / проверка / объединена / заблокирована
Доказательства и передача: <команды, результаты, ограничения, следующий шаг>
Глава проекта / приёмка: lovlyDev
Ответственный за релиз: Анна
```

Обновляйте Issue при блокировке, передаче и завершении. Не поручайте обоим людям независимо реализовать одинаковые критерии приёмки. Общая таблица задач в репозитории допустима, но в этом процессе основная запись — Issue: дополнительного общего файла блокировок нет.

## Раздельные ветки и worktree

На новом ПК клонируйте разрешённый URL репозитория в новую папку. Не клонируйте поверх существующего рабочего каталога. В примерах PowerShell используется `main`; замените её фактической интеграционной веткой команды. Выполняйте команды по одной и останавливайтесь при ошибке. Это инструкции, а не команды, выполненные при создании руководства.

```powershell
git clone <repository-url> Forma
Set-Location Forma
git status --short
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c task/123-anna-section-ui
```

Для второй задачи на одном ПК создайте отдельный worktree после закрепления новой задачи. Папка назначения должна быть новой. Исходная ветка и её локальные файлы сохраняются:

```powershell
git fetch origin
git worktree add -b task/124-boris-section-core ..\Forma-124 origin/main
Set-Location ..\Forma-124
```

У каждого worktree свои файлы и ветка; объекты Git общие. Подготовьте зависимости в новом worktree по [руководству разработчика](development.md). На одном ПК согласуйте тяжёлые нативные сборки, чтобы они не конкурировали за общие каталоги результатов и кеша. Не заменяйте Git синхронизацией живой рабочей папки или базы SQLite.

Перед обновлением существующей ветки задачи выполните `git status --short`. Если есть незакоммиченные файлы, завершите небольшой осмысленный коммит либо сохраните их по согласованию с владельцем. Не применяйте разрушительный reset, clean или добавление всех файлов ради чистого рабочего дерева. Для чистого дерева:

```powershell
git fetch origin
git rebase origin/main
```

Разрешите конфликты в своих файлах и повторите нужные проверки. Конфликты общих файлов согласуйте с владельцем. Не переписывайте ветку, которой пользуется другой человек. Rebase удобен для личной ещё не отправленной ветки; если уже опубликованную ветку нужно обновить, согласуйте с проверяющим merge `origin/main` вместо force push.

## Ограничьте задачу каждого агента

Скопируйте этот стартовый запрос в сессию каждого человека и замените значения:

```text
Прочитай AGENTS.md, docs/ru/status.md, docs/ru/collaboration.md и GitHub Issue #<номер>.
Задачу закрепил <человек>; ветка <ветка>; исходный коммит <SHA>.
Работай только в <мои файлы/модули>; <другой человек/агент> отвечает за <чужие модули>.
Реализуй <цель> и проверь <критерии приёмки>. Подтверди согласованный API в Issue.
Сохрани текущую ветку и все существующие локальные файлы. Не перезаписывай чужую работу.
Если Issue или API недоступны, изучай локальные исходники без изменений и сообщи,
какой контракт нужен, прежде чем менять зависимые файлы. Не выдумывай прогресс другого агента.
Не меняй общие версии, миграции, lockfile и релизы без назначения их владельца.
Передай нужные общие изменения <владелец>. Добавляй RU/EN документацию и тексты
в пределах согласованного владения. Запускай проверки, соответствующие задаче.
Сообщи изменённые файлы, реальные команды/результаты, ограничения и следующий шаг передачи.
Не публикуй в GitHub, не объединяй PR, не создавай теги/релизы и не устанавливай приложение
без явного разрешения этого человека. За релиз отвечает <человек>.
Личные заметки .local не заменяют общую передачу задачи.
```

Человек проверяет, что агент находится в нужной папке и ветке. Для чтения Issue может потребоваться коннектор либо вставленный текст без секретов; не передавайте агенту чужие учётные данные. Если нужен комментарий Issue или PR, явно разрешите его отправку. Локальные субагенты соблюдают те же границы; их количество не синхронизирует две независимые сессии автоматически.

## Проверка и объединение

Делайте небольшие коммиты с одной целью. Перед добавлением явных путей просматривайте diff; личные артефакты и секреты не должны попадать в коммит:

```powershell
git diff --check
git diff
git add docs/en/collaboration.md docs/ru/collaboration.md
git diff --cached
git commit -m "docs: explain two-PC collaboration"
```

После разрешения человека на удалённую публикацию отправьте ветку и откройте PR в интеграционную ветку:

```powershell
git push -u origin task/123-anna-section-ui
```

В [шаблоне PR](../../.github/pull_request_template.md) репозитория уже есть поля для передачи. В PR укажите Issue, конкретное поведение до/после, окончательный объём изменений, реальные проверки и ограничения. Глава проекта lovlyDev проверяет результат и принимает решение об объединении. Он может сам проверить код и поведение или по своему желанию назначить проверяющего; обязательного второго человека нет. Одного ответа AI «готово» недостаточно. Сами шаблоны не создают Issues, не отправляют комментарии, не меняют права и не обеспечивают обязательное ревью.

Используйте подходящие проверки из [руководства разработчика](development.md), включая документацию, i18n и миграции, когда они затронуты. [Quality](../../.github/workflows/ci.yml) автоматически запускается для PR в `main` и отправки коммитов в `main`; также доступны ручной запуск и вызов из другого workflow. Матрица native CAD выполняется только при ручном запуске с соответствующим параметром. Проверяйте фактические результаты заданий и при необходимости запускайте эту дополнительную нативную проверку; отсутствие или пропуск обязательных проверок у PR не означает успех.

## Один ответственный за релиз

Ответственный за релиз объединяет проверенные задачи, согласует зависимости и выделяет новые имена миграций без изменения применённых файлов. Он синхронизирует версии npm workspace/lockfile, Cargo и Tauri, выполняет обязательные проверки, собирает новый Windows-установщик, сохраняет старые артефакты и проверяет полученный файл. Владельцы задач передают готовую работу; обязательное повышение версии и сборка выполняются согласованно при интеграции, а не конкурирующими правками каждого агента.

Только этот ответственный публикует согласованный релиз. [Release](../../.github/workflows/release.yml) запускается отправкой нового подходящего версионного тега и вызывает проверки/сборки; отправка тега является действием публикации, а не обычной синхронизацией. Не создавайте повторные теги и не перезаписывайте прежние релизы. Администратор может настроить защиту веток и обязательное ревью; руководство не утверждает, что они уже включены.

## Передавайте доказательства, личные данные оставляйте локально

Handoff из `.local`, личные журналы и память чата остаются на конкретном ПК. В Issue/PR размещайте очищенную сводку: SHA коммита, владельцев файлов, контракт API, выполненные тесты, нерешённые вопросы и следующего ответственного. На втором ПК получите проверенные коммиты и перечитайте сводку; не копируйте предполагаемое состояние другого чата.

Не коммитьте базы приложения, пользовательские CAD-файлы, кеши сборки, токены, ключи провайдеров или подписи. Для тестов используйте искусственные данные, для релизов — согласованное хранилище артефактов. Завершая сессию, сохраните ветку, опишите незаконченную работу и явно освободите задачу, если её должен продолжить другой человек.
