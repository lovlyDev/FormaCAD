## Зависимости
Node.js 22+, Rust 1.97.1 и [системные зависимости Tauri](https://v2.tauri.app/start/prerequisites/). Windows требует Visual C++ Build Tools и WebView2, macOS — Xcode command-line tools. Пакеты macOS рассчитаны на 11+.

Ubuntu 22.04+:
~~~sh
sudo apt-get update
sudo apt-get install -y build-essential curl wget file libssl-dev libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf libfuse2 rpm
npm ci
npm run desktop
~~~

При нескольких установках Visual Studio:
~~~powershell
. ./scripts/windows-env.ps1
npm run desktop
~~~
[Скрипт](../../scripts/windows-env.ps1) выбирает полный набор C++-заголовков и библиотек.

## Воспроизводимый Rust
Локальные Rust-проверки и проверенный Windows-пакет используют Rust 1.97.1 и Clippy 0.1.97. [Quality](../../.github/workflows/ci.yml) и [Release](../../.github/workflows/release.yml) закрепляют ту же версию вместо плавающей `stable`; строгий `-D warnings` сохранён. Это согласует окружение проверки, но не заменяет успешный прогон каждой платформы в CI.

После установки rustup выполните из каталога своего клона:
~~~sh
rustup toolchain install 1.97.1 --profile minimal --component rustfmt --component clippy
rustup override set 1.97.1
rustc --version
clippy-driver --version
~~~
Override действует для этого клона; глобальную версию других проектов менять не требуется. Ожидаемые версии: `rustc 1.97.1` и `clippy 0.1.97`. Tauri и npm-команды сборки используют выбранный здесь Cargo.

Обновление Rust оформляйте отдельной задачей с владельцем: согласуйте новую фиксированную версию в обоих workflow и этом руководстве, выполните rustfmt, строгий Clippy для всех targets, Rust-тесты с `--locked` и проверки native CAD в подготовленном окружении. Более новый Clippy может вводить дополнительные предупреждения; исправляйте причины, сохраняя строгий режим, и подтверждайте результаты CI перед слиянием.

Rust-тесты CI используют `runner.temp` как `TMPDIR`: на macOS системный временный путь может проходить через символьную ссылку `/var`. Это выбирает обычный корень для тестовых проектов, сохраняя запрет символьных ссылок в коде приложения и соответствующие отрицательные проверки. Для локального запуска на macOS можно задать `TMPDIR` как существующий проверенный каталог без ссылок; не отключайте проверку безопасных путей ради тестового окружения.

## CAD-окружение
Используйте Python 3.12 и [requirements-cad.txt](../../requirements-cad.txt):
~~~sh
python -m venv .venv
# Windows
.venv/Scripts/python -m pip install -r requirements-cad.txt
# macOS / Linux
.venv/bin/python -m pip install -r requirements-cad.txt
~~~
Выберите интерпретатор в «Настройки → CAD-окружение». Путь сохраняется при обновлениях. FORMA_PYTHON — необязательный резервный вариант. CLI нужно установить и авторизовать отдельно. Запуск с рабочего стола также ищет инструменты в стандартных каталогах Homebrew и локальных программ без выполнения shell-профилей.

## Проверки
~~~sh
npm run check:version
npm run check:i18n
npm run check:docs
npm run lint
npm test
npx playwright install chromium
npm run test:e2e
cargo +1.97.1 fmt --manifest-path apps/desktop/src-tauri/Cargo.toml --check
cargo +1.97.1 clippy --manifest-path apps/desktop/src-tauri/Cargo.toml --all-targets -- -D warnings
cargo +1.97.1 test --manifest-path apps/desktop/src-tauri/Cargo.toml --locked
python scripts/test_cad.py
npm run package
~~~

CAD-тестам нужен подготовленный Python. Для геометрических проверок из Rust задайте FORMA_TEST_PYTHON. Установщики собираются на целевой ОС; нужные машины предоставляет [GitHub workflow](../../.github/workflows/release.yml). Подписанные релизы описаны в [руководстве](releases.md).

Браузерные проверки используют реальные пользовательские действия. Общий `e2e/customSelect.ts` дожидается окончания анимаций самого элемента и его контейнеров, выбирает пункт открытого кастомного меню и проверяет итоговый текст закрытого селектора. Не заменяйте такой маршрут `selectOption` для кнопки-комбобокса, принудительным кликом или прямым изменением состояния. Проверка редактора сохраняет требования к высоте 32 px, выравниванию и повторным анимациям; скриншот строки снимается после проверки её полной видимости, без повторной прокрутки локатором. Chromium со SwiftShader не заменяет приёмку установленного WebView.

Браузерные тесты используют явно включённый **WebGL fallback** SwiftShader (`--use-gl=angle --use-angle=swiftshader-webgl --enable-unsafe-swiftshader`) по [руководству Chromium](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/swiftshader.md). WebGL2 остаётся настоящим программным рендером, а обычное содержимое страницы использует программный compositor. Прежний режим замены GPU (`--use-angle=swiftshader`) задерживал первый `Page.captureScreenshot` примерно на 56 секунд в воспроизведённом Windows-сценарии; в том же disclosure-тесте с fallback захват занял 28 мс. Изменена конфигурация браузерных тестов: исходные таймауты, проверки настоящих анимаций и скриншоты сохранены. `e2e/webgl-renderer.spec.ts` проверяет реальный контекст WebGL2, renderer SwiftShader и цвет пикселя треугольника, нарисованного шейдерами. Флаг unsafe fallback ограничен тестами этого доверенного локального приложения; рендер выпускаемого приложения не меняется. Эта проверка не подтверждает установленный WebView или успешность на всех платформах CI.

## Изменения интерфейса
Windows-пакет нативного приложения отдельно собирает worker с `native-occt` и включает его через `externalBin`. Desktop собирается только с `native-worker-client`: Tauri исключает Cargo-бинарник worker, требующий `native-occt`, из этого шага. Поэтому `externalBin` здесь обязателен и остаётся единственным маршрутом упаковки worker; прежнее дублирование двух маршрутов недопустимо. Проверяйте, что сгенерированный NSIS содержит ровно одну инструкцию File для worker, затем запускайте smoke именно этого бинарника с упакованными DLL и записывайте его SHA-256. Проверка промежуточного fixture не доказывает состав установщика. Старые версионные установщики сохраняются; локальная проверка не включает установку приложения.

Добавляйте строки в [en.json](../../apps/desktop/src/i18n/en.json) и [ru.json](../../apps/desktop/src/i18n/ru.json), включая подсказки, ошибки и accessibility. Используйте t(), локальное форматирование и цвета темы. Не переводите имена файлов, код, CAD ID и сообщения пользователя/AI. Проверяйте оба языка и обе темы. Скриншоты сохраняются в исключённом docs/verification/.

## Изоляция загрузки CAD на Windows

Сборка desktop использует `native-worker-client`: чистые Rust-клиенты и проверяемые контракты, без CXX/OCCT. Отдельный `forma-cad-worker` собирается с `native-occt`, который включает клиентский контракт и ядро. Построение, импорт STEP, свойства, измерения и сечения продолжают вызывать worker; отключение этих возможностей не является способом получить независимый host. Bridge находится в `src/native/kernel.rs`, чистые входные проверки измерений — в `native/reference_measurements/inputs.rs`.

Windows packaging отдельно собирает worker, затем desktop с клиентской feature. [Подготовка runtime](../../scripts/stage-windows-runtime.ps1) берёт DLL только из лицензированного Visual Studio `x64/Microsoft.VC143.CRT` / `x64/Microsoft.VC145.CRT`, проверяет подпись Microsoft и PE x64 до копирования, сверяет SHA-256 и не заменяет отличающиеся уже подготовленные DLL. Путь можно передать параметром `RuntimeDirectory` в `build-native-windows.ps1`. Файлы размещаются рядом с worker через ресурсы пакета; пользовательская установка Visual Studio и сетевое получение runtime при запуске не требуются. Локальное распространение runtime требует соблюдения лицензии Visual Studio и выпуска исправлений этих DLL вместе с приложением; см. [Microsoft](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files).

Проверка: сборка client-only без OCCT_ROOT, kernel-тесты и реальные worker-сценарии, таблица прямых и транзитивных импортов свежего извлечённого desktop (без OCCT), подписи и зависимости упакованного runtime. Отдельно требуется проверка настоящего интерфейса при отсутствии CAD DLL и установленного приложения на чистой Windows. Успешная исходная сборка не доказывает эти последние пункты. Authenticode приложения/OCCT и политика Smart App Control остаются отдельными границами; подпись updater их не заменяет. Пакет 1.3.0 не изменяется этим исправлением.

Проверка готовности использует `--health-check`: worker проверяет реальный единичный куб в памяти и возвращает ограниченный JSON без записи STEP, GLB или проекта. Host проверяет успешный выход процесса, версию протокола, ядро, версию приложения и схему ответа. Наличие EXE само по себе не считается готовностью. Ошибка `NATIVE_KERNEL_UNAVAILABLE` переводится на границе отображения; технический ответ сохраняется отдельно. Проба имеет тайм-аут восемь секунд и использует существующее завершение дерева процессов.

Проверка запускается в отдельном временном каталоге и удаляет его после завершения процесса. Это изолирует записи старого worker, который ещё не понимает `--health-check`, от папки установки и пользовательского проекта. Несовместимый ответ остаётся ошибкой готовности. Ошибка удаления временного каталога также возвращается как техническая ошибка готовности.

Поддерживаются лицензированные runtime семейств VC143 и VC145. До копирования проверяется, что версия каждой DLL не старее выбранного компилятора; это также относится к явно переданному `RuntimeDirectory`. Совместимость v14 между MSVC 2015–2026 описана [Microsoft](https://learn.microsoft.com/en-us/cpp/porting/binary-compat-2015-2017). Старый runtime рядом с новым worker не считается допустимым только по имени DLL.

## Отдельный профиль приложения

`FORMA_DATA_DIR` задаёт абсолютный каталог всего профиля Forma: база `forma.sqlite`, проекты, журналы, настройки окна и локальный профиль WebView. Переменная предназначена для отдельных локальных профилей и проверок; без неё остаются стандартные каталоги приложения. Для нового профиля укажите отдельную папку перед запуском EXE. Возвращайтесь к тому же пути, чтобы продолжить с теми же настройками; другой путь открывает независимый профиль. Существующие данные основного профиля не копируются автоматически.

Модуль `app_profile` проверяет путь до создания Tauri Builder, окон и плагинов. Пустой или относительный путь отклоняется с ошибкой запуска, без перехода на основной профиль. В Tauri 2.12 используется официальный [AppDirectoriesOverride через Context](https://docs.rs/tauri/2.12.0/tauri/struct.Context.html#method.config_mut): config/data/local-data направлены в выбранную папку, cache — в `caches`, журналы — в `logs`. База также берёт путь из Tauri resolver. Штатный window-state plugin остаётся включённым; файлы WebView и `.window-state.json` принадлежат этому профилю. Семейство Tauri runtime/macros/utils/build обновлено согласованно; это не подмена Windows Known Folders через окружение.

Проверка включает отказ до записи для некорректных путей, настоящий resolver и сохранение window-state через MockRuntime, миграции и чтение/запись SQLite в выбранном профиле. Эти проверки не заменяют запуск настоящего WebView и повторное открытие окна из извлечённого EXE. Для приёмки реального процесса используйте отдельный тестовый профиль Windows/VM, сравнение каталогов до/после и два запуска с восстановлением состояния. Перенаправляются хранилища приложения; системные журналы Windows и внутренние системные записи браузера не являются гарантией полной изоляции процесса. Каталог профиля может содержать ключи и данные пользователя: его нельзя коммитить или пересылать вместе с исходниками.

Проверки окружения в настройках запускаются только на страницах AI и CAD. Страницы оформления, конфиденциальности и разрешений не запускают внешние CLI ради неиспользуемого результата; аудит разрешений сохраняет собственный маршрут запроса. Браузерная проверка проходит через настоящие кнопки и подтверждает отсутствие запроса до перехода на CAD в обоих языках и темах.

Windows integration tests, использующие настоящий Tauri MockRuntime, также получают встроенный manifest Common Controls v6. Tauri добавляет стандартный ресурс только бинарникам приложения, а `muda` импортирует `TaskDialogIndirect`, отсутствующий в старой системной версии Common Controls. Без manifest тест завершался кодом `0xc0000139` до начала тестового harness. Test-only linker arguments исправляют загрузку, не заменяя manifest выпускаемого приложения.

В Windows внешний `WEBVIEW2_USER_DATA_FOLDER` или политика WebView2 может переопределить папку браузера. Для контролируемой приёмки проверяйте эти overrides отдельно по [документации Microsoft](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl). Проверка формы профиля не является sandbox внешних AI-программ: их health-команды выполняются отдельно при открытии соответствующих страниц.
