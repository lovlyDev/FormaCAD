Полная 2.0 не готова; см. [состояние](status.md).

## Однократная настройка GitHub
Репозиторий: [lovlyDev/FormaCAD](https://github.com/lovlyDev/FormaCAD). Загрузите исходники и включите Actions. Для анонимного скачивания обновлений репозиторий должен быть публичным; GitHub-токен в приложение не встраивается.

В Settings → Secrets and variables → Actions добавьте:
| Имя | Тип | Значение |
| --- | --- | --- |
| TAURI_SIGNING_PRIVATE_KEY | Secret | Полное содержимое приватного ключа обновлений |
| TAURI_SIGNING_PRIVATE_KEY_PASSWORD | Secret | Пароль ключа, если задан |
| TAURI_UPDATER_PUBLIC_KEY | Variable, необязательно | Публичный ключ; по умолчанию используется ключ из конфигурации |

Первый локальный ключ создан в .secrets/updater.key, публичная часть записана в [tauri.conf.json](../../apps/desktop/src-tauri/tauri.conf.json). Приватный файл и журнал генерации исключены из Git. Сохраните резервную копию ключа отдельно. Его нельзя публиковать или генерировать заново для каждой версии: установленные приложения доверяют именно этому ключу.

Для новой независимой линии распространения:
~~~sh
npm run tauri -w apps/desktop -- signer generate --ci -w ../../.secrets/updater.key
~~~
Не перезаписывайте ключ, которым уже подписывались выпущенные версии. [Документация Tauri updater](https://v2.tauri.app/plugin/updater/).

## Лицензии OCCT в пакете

Нативные конфигурации Windows и Unix задают каждому файлу полный путь назначения: `licenses/occt/LICENSE_LGPL_21.txt` и `licenses/occt/OCCT_LGPL_EXCEPTION.txt`. Общий путь для двух отдельных файлов вызывал совпадение имён в NSIS-архиве; исходники 1.3.0 исправляют его. Лицензии входят в пакет и не затрагивают базы пользователя. Извлеките Windows EXE без запуска установщика; проверьте единственность обеих лицензий и соответствие SHA-256 файлам `resources/occt`. Сравните извлечённые app, worker и 25 DLL с результатом сборки и проверьте геометрию на извлечённом worker. Исправление Unix-конфигурации не доказывает проверку пакетов macOS/Linux.

Tauri заменяет в упакованном app ровно метку `__TAURI_BUNDLE_TYPE_VAR_UNK` на `__TAURI_BUNDLE_TYPE_VAR_NSS`, затем восстанавливает build output. Сравнивайте полный SHA-256 извлечённого приложения с ожидаемым результатом этой единственной замены; любые другие отличия запрещены. [Первичный исходник Tauri](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle.rs).

## Передача между двумя ПК и проверка исходников

Следуйте [правилам совместной работы](collaboration.md) и [AGENTS.md](../../AGENTS.md). По умолчанию задачу реализует один активный владелец на одном ПК; второй человек может читать результат либо получает явно переданную задачу; приёмку выполняет глава проекта lovlyDev. У каждого отдельный клон. Не переключайте занятую ветку, не сбрасывайте чужие изменения и не переносите личную БД через Git.

В Issue и PR укажите владельца, ветку задачи, исходный и окончательный SHA, разрешённые файлы, фактические проверки, ограничения и следующего ответственного. Передача на второй ПК означает передачу проверяемого коммита, а не предположений из другого чата. Незакоммиченные файлы остаются на исходном ПК. Получатель подтверждает владение до правок; прежний владелец прекращает запись в переданную область. Общие версии, lockfile, номера миграций и релизные метаданные изменяет назначенный интегратор.

Глава проекта lovlyDev проверяет PR против точного SHA и принимает решение о слиянии; второй проверяющий необязателен. Сводка агента помогает ревью, но не заменяет его. Только интегратор объединяет изменения и фиксирует окончательный релизный SHA. При изменении исходников после проверки повторите затронутые проверки; артефакт должен соответствовать итоговому коммиту. Не используйте прямой push в основную ветку как замену PR и ревью.

## Подготовка нового выпуска

Ответственный выбирает новый номер, не использованный выпущенным релизом, и синхронизирует npm workspace/lockfile, Cargo и Tauri через `npm run version:set -- X.Y.Z`, заменив `X.Y.Z` реальным номером. Эта команда не разрешает публикацию сама по себе. Подготовьте двуязычную документацию возможностей и `docs/releases/X.Y.Z.md` с реальными результатами и ограничениями.

Выполните проверки из [руководства разработчика](development.md), включая `check:version`, `check:i18n`, `check:migrations`, `check:docs`, frontend lint/types/unit/build, обязательные браузерные сценарии RU/EN и обеих тем, native-тесты, строгий Clippy, проверку без default features и fmt. При повторе ошибки сохраняйте первоначальный результат; успешный узкий повтор не означает успех всего прогона. На одном ПК один назначенный исполнитель запускает тяжёлые native-сборки последовательно.

Соберите новый Windows EXE в отдельный версионный каталог. Проверьте размер и SHA-256, FileVersion/ProductVersion, подпись updater существующим ключом и соответствие metadata реальному пакету. Проверяйте свежий worker, извлечённый из **этого** установщика: его SHA, ровно один worker и ожидаемые 25 OCCT DLL, возможности, положительные аналитические сценарии и безопасные отказы. Debug-worker и старый установщик не подтверждают новый пакет. Сохраните очищенную сводку проверок и ссылку на EXE; старые релизы не перезаписывайте. Проверка упаковки не означает установку и запуск в установленном WebView.

## Выберите один маршрут публикации до отправки тега

Разрешение человека на текущую публикацию и назначение ответственного должны быть явными; прошлое разрешение на 1.2.6 не является постоянным разрешением на следующие релизы. Перед отправкой нового тега проверьте фактическое состояние Actions и наличие релиза/черновика для выбранного номера. Создание релиза вручную не отключает tag-triggered workflow. Не запускайте одновременно ручную загрузку Windows-пакета и автоматического публикатора того же номера.

Для автоматического маршрута ответственный создаёт новый тег `vX.Y.Z` на окончательном проверенном SHA после PR и ревью и отправляет только согласованный тег. Отправка тега запускает публикацию. Дождитесь фактического успеха Quality, всех четырёх платформенных сборок и финального job; проверьте опубликованные файлы, контрольные суммы и metadata. Само наличие тега или начавшийся workflow не подтверждает готовность релиза.

[Release](../../.github/workflows/release.yml) запускает [Quality](../../.github/workflows/ci.yml), затем собирает нативные CAD-пакеты для Windows x64, Linux x64, macOS ARM64 и Intel. Windows использует [свою сборку OCCT](../../scripts/build-occt-windows.ps1), macOS и Linux — [зафиксированную статическую сборку](../../scripts/build-native-unix.sh). Перед упаковкой worker проходит [проверку геометрии и контрольных сумм](../../scripts/check-native-unix.py). Создаются подписи обновлений, пакеты с уникальными именами, общий latest.json и SHA256SUMS. Релиз остаётся черновиком до загрузки всех файлов. Выпущенные версии не перезаписываются; перед повтором неудачного тега нужно разобраться с оставшимся черновиком.

Quality автоматически проверяет pull request в `main` и push в `main`; эти проверки не публикуют пакеты. Quality также запускается вручную в Actions и вызывается релизным workflow. Автоматические сборка установщиков и публикация остаются привязанными к тегам: новый тег `vX.Y.Z` запускает Release, номер проверяется на совпадение с приложением. Ручной Quality может включать нативную матрицу; `nativeCadMatrix` выбирает объекты `{ "os", "target" }`. Обновление или удаление существующего тега не публикует релиз. Отдельно разрешённый ручной выпуск проверенного Windows-пакета описан ниже.

## Отдельно разрешённый Windows-маршрут

Для Windows-only выпуска ответственный загружает только проверенные локальные EXE, updater-подпись, SHA256SUMS и Windows metadata, соответствующие точному релизному SHA. До отправки нового тега согласуйте предотвращение второго публикатора: если Release уже запущен для этого номера, проверьте его реальное состояние и остановите конкурирующую публикацию в пределах выданного разрешения. Не утверждайте, что ручной `create release` избегает workflow. Если релиз уже существует, не заменяйте его файлы и не переиспользуйте тег.

Исторический **1.2.6** опубликован этим отдельным маршрутом: EXE и подпись updater проверены, в пакете один worker и 25 OCCT DLL; упакованный worker прошёл 64 аналитических случая и 19 отказов. См. [доказательства артефакта](status.md). Для **1.3.0** нужны собственные завершённые проверки и новый артефакт; эти доказательства нельзя заимствовать у 1.2.6. Windows-only выпуск не доказывает готовность macOS/Linux или завершение четырёхплатформенной матрицы.

Описанный выше Release workflow остаётся маршрутом будущей автоматической матрицы по новому тегу. Он собирает платформы, подписывает updater-артефакты и объединяет metadata. Ручная загрузка текущего Windows-пакета не доказывает прохождение этой матрицы; установку на компьютер пользователя она не выполняет.

## Поведение приложения
Проверка выполняется при запуске и каждые шесть часов. Новая версия предлагает «Установить / Позже», когда нет активной операции или редактора. «Позже» откладывает окно, кнопка обновлений остаётся доступной. Перед установкой проверяется подпись пакета, сохраняются настройки и создаётся копия SQLite. Windows перезапускается через NSIS; macOS и AppImage — после замены приложения.

DEB/RPM обновляются установкой нового пакета. Отсутствие релиза, сети или доступного GitHub не мешает запуску. Для ручного перехода используйте установщик конкретного проверенного опубликованного выпуска. Идентификатор приложения и пути данных сохраняются; перед установкой сделайте резервную копию каталога данных. Публикация релиза не разрешает агенту самостоятельно устанавливать его на ПК пользователя.

Версия 1.0.0 может закрываться при запуске, если существующая база SQLite содержит миграцию, созданную с окончаниями строк LF. Если приложение не успевает предложить обновление, установите [1.1.0](../releases/1.1.0.md) вручную. Установщик сохраняет каталог данных и проекты.

## Системные подписи
Подпись обновления обязательна, но она не заменяет Apple Developer или Windows Authenticode.

Без учётных данных Apple workflow создаёт приложения с ad-hoc подписью для обеих архитектур macOS. При установке Gatekeeper может потребовать отдельное разрешение. Для нотарифицированных сборок добавьте секреты APPLE_CERTIFICATE (P12 в base64), APPLE_CERTIFICATE_PASSWORD, APPLE_SIGNING_IDENTITY, APPLE_ID, APPLE_PASSWORD (пароль приложения), APPLE_TEAM_ID. См. [подпись macOS](https://v2.tauri.app/distribute/sign/macos/).

Windows собирается и без коммерческого сертификата; репутация SmartScreen не связана с проверкой подписи обновления. См. [подпись Windows](https://v2.tauri.app/distribute/sign/windows/).
