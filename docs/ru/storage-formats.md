# Сравнение форматов хранения

[Документация](index.md) · [English](../en/storage-formats.md) · [Программа](storage-program.md)

Целевой формат выбран в [решении](storage-format-decision.md); production backend ещё не подключён. Сравниваются существующие
manifest/generations v2 и экспериментальная SQLite внутри папки проекта.
SQL-кандидат теперь использует минимальные project/history таблицы и типизированную историю; общая база
приложения не участвует в его синтетических данных. Это benchmark, а не доступный
пользователю open/save маршрут. Первый сохранённый baseline использовал app schema;
он сохраняется отдельно и не считается проверкой нового чистого opener.

Исправленный кандидат `sqlite-delete-prototype` использует rollback journal DELETE
и synchronous FULL. Явное create не переиспользует существующий файл. Reader
проверяет ограниченный SQLite header, application_id/user_version и отсутствие
WAL/SHM/journal до подключения, затем read_only/query_only и quick_check. Режим
immutable не используется. Reader не применяет миграций и не чинит журнал;
WAL purity остаётся неподдержанной. Это прототип benchmark, не готовый writer API.
Четыре регрессии проверяют неизменность файлов, отсутствие app-таблиц, запрет
записи и контролируемый отказ на чужом/будущем/WAL формате. Открытие writer
измеряется отдельно от сохранения metadata.
SQL copy/export preflight консервативно оценивает JSON escaping как шесть байт
на байт текста. Поэтому допустимый архив около лимита может быть отклонён раньше
общего лимита 16 МиБ. Сравнение использует одни small/medium/large фикстуры;
это ограничение прототипа, а не новый общий лимит пользовательской истории.

## Границы чтения

### Что требуется проверить до выбора формата

Аудит существующей v2 выявил две границы crash safety. Общий CAS сейчас
создаётся сразу под окончательным `assets/<hash>`: частичная запись может оставить
невалидный объект, который повторное staging отклонит. Старый опубликованный
manifest не делает такой объект новым commit. Будущее исправление должно сначала
записать и проверить собственный temp, затем установить окончательное имя без
перезаписи существующего CAS; reader не удаляет и не восстанавливает остатки.
Один `sync_all` файла не доказывает сохранность directory entry при потере питания.

В legacy recovery исходный manifest сравнивается до получения storage lock.
Перед публикацией требуется повторить сравнение под lock и очистить только тот
pending target, который действительно обработан. Иначе более новый внешний
commit может быть заменён старым. Эта находка не означает исправленный recovery.
SQL-кандидат тоже ещё не получает гарантию: его обычный opener отказывает при
journal; явное восстановление и аварийные точки требуют отдельного исполнения.
Выбор не может опираться только на более короткое время metadata save.

Новый opt-in crash benchmark завершает собственный дочерний test process
в четырёх точках: manifest staging/после publish и SQL transaction/после commit.
Для незавершённой SQL transaction требуется реальный hot-journal header и
изменённые страницы БД; reader обязан отказать без записи. Затем отдельно
вызывается SQLite recovery только на принадлежащей тесту фикстуре и проверяются
старые metadata, точный архив истории и CAS. После commit ожидается новое
metadata. Вывод разделяет время процесса, read/recovery и явного SQL recovery.
Первый выполненный результат приведён ниже; это process death, а не обесточивание, production recovery
или свидетельство реального CAD commit/USB/NAS.

Новый `project_storage_v2::reader::FolderSnapshot` захватывает manifest и
project.json, проверяет ограниченные размеры, SHA и ссылки metadata. Он не читает
посторонние assets и архив событий. `read_asset` принимает только точный descriptor
из снимка и проверяет обычный файл, размер, SHA, исходный manifest и metadata.
`read_history` явно проверяет архив и его связи. `recheck` также обнаруживает
повреждение project.json при неизменённом manifest. Исходник не восстанавливается
и не изменяется. Отсутствующий asset не скрывается: metadata может быть прочитана,
но явное чтение повреждённого вложения завершается ошибкой.

Это низкоуровневый читатель сохранённых байтов. Repository adapter обязан отдельно
удерживать исходный lifecycle token и OS identity расположения. Существующий
`read_folder` сохраняет полную проверку всех записей. Существующая v2 хранит cursor
в полном архиве истории: benchmark не выдаёт чтение этого архива за O(1) status.

copy/export transaction. Выполненные copy/export измерения приведены ниже; crash recovery,
холодный кеш и production publication не получают выдуманного времени.

## Общая интеграция

Для следующего подключения настоящего CAD executor подготовлен отдельный
[точный контракт и патч](../integration/storage-folder-execution.md) на шесть
файлов. Он применён после отдельного разрешения lovlyDev на все шесть путей,
включая два native asset файла области Issue №3 по §5 ТЗ. Это не означает готовность
папочного model commit.

### Основа самостоятельного SQLite backend (этап 4, проверка)

В `project_repository/sqlite_folder` подготовлена отдельная схема FCP1
(`application_id=0x46435031`, `user_version=1`). Она хранит UUID репозитория,
проекта и коммита раздельно, проверяет полный fingerprint схемы и связывает
проект, курсор и архив истории хешами. SQL-публикация различает подтверждённый
коммит, отказ до COMMIT и неопределённый результат COMMIT; последний нельзя
автоматически повторять. Инициализация отказывается менять непустую чужую БД.

Читатель использует отдельный недефолтный SQLite VFS с запретом записи,
восстановления журналов, SHM и ATTACH. Он проверяет фактически открытый файл,
сохраняет привязку к каталогу и читает CAS через файловые примитивы SQLite,
чтобы закрытие случайного hardlink на Unix не снимало блокировки другой связи.
Поддержка этого слоя ограничена Linux и Windows; остальные платформы отказывают
явно. Привязка VFS проверяется к SQLite 3.46.0 из текущего lockfile.
Основная БД также обязана иметь единственную файловую ссылку: hardlink под
другим именем мог бы скрыть исходный rollback/WAL журнал. Отказ не удаляет
ни исходную БД, ни её журнал, ни второй путь.
Запись сравнивает полный захваченный снимок внутри `BEGIN IMMEDIATE`, а не
только UUID коммита. Изменение метаданных с прежним UUID и пересчитанными хешами
поэтому не даёт разрешения перезаписать источник. Проверка через commit hook
SQLite моделирует отказ COMMIT: возвращается известный UUID неопределённой
операции, а повторное чтение определяет фактическое состояние без replay.
Проверка известного UUID различает текущий head, более ранний сохранённый
коммит и отсутствие коммита в проверенной цепочке. Она выполняется в одной
SQL-транзакции и проверяет UUID репозитория/проекта. Даже отсутствие записи не
разрешает автоматический повтор операции. Сеанс разрешает такое чтение после
продвижения head, но отклоняет его после закрытия или через другое открытие.

`project_access/folder_lease` удерживает отдельную блокировку выбранной папки.
Инициализация требует уже существующую пустую папку; она не обещает атомарно
зарезервировать внешний namespace. Операции сохраняют закреплённые каталоги,
проверяют подмену и отказываются следовать ссылкам.

Эти модули пока зарегистрированы **только в тестовой сборке**. Пользовательского
действия открытия или записи FCP1 ещё нет. Тесты проверяют SQL-контракт, отказы
чтения при sidecar/WAL, сохранение исходных файлов и независимость блокировок;
они не доказывают CAD commit, восстановление после аварии или готовность этапа 4.
Локальная компиляция требует Windows MSVC linker; CI должен подтвердить новый
код до подключения production-маршрута.

`sqlite_folder/cas` валидирует полный кандидат и весь пакет pending bytes до
IO. Существующие объекты проверяются только через VFS; новые создаются с
`create_new`, записываются и синхронизируются до появления SQL-ссылок. Пакет
удерживает каталог, writer lease и исходные handles новых файлов до разрешения
SQL outcome. Ошибка оставляет неподключённый объект для явного recovery, а не
перезаписывает или удаляет прежний файл. Bootstrap требует все байты кандидата
и отказывается от любого существующего digest. Linux синхронизирует каталог
assets; Windows использует write-through и flush новых файлов. Проверка
process-crash не является приёмкой power-loss любого устройства. Синхронизация
корня после создания самого assets остаётся частью будущего bootstrap.

`sqlite_folder/write_connection` открывает существующую FCP1 сначала без права
изменять данные или восстанавливать журналы. Под `BEGIN IMMEDIATE` он проверяет
схему и полный захваченный снимок, затем разрешает только собственный DELETE
rollback journal. VFS удерживает lease до фактического закрытия base file даже
при отмене SQLx connect или асинхронном Drop. Неизвестный journal/WAL/SHM,
другой head или схема вызывают отказ. Linux unlink журнала остаётся проверкой
под кооперативной блокировкой, без обещания атомарного unlink-if-inode-matches
против несогласованной внешней подмены namespace. Этот слой пока также test-only.

Создание новой БД использует отдельную приватную ветвь того же VFS: единственный
`MAIN_DB | READWRITE | CREATE | EXCLUSIVE`, затем проверка фактически открытого
пустого файла и его identity. Имеющийся или появившийся между проверкой и open
файл не принимается. Только эта ветвь получает DDL authority для immutable FCP1
схемы; после initialize проверяется сохранённый снимок и включается обычная
политика. Неподтверждённый исход блокирует дальнейшее использование соединения;
ошибка после COMMIT сохраняет UUID как Indeterminate. Linux дополнительно flush
assets/.forma/root. Четыре новые проверки охватывают fresh read, отказ существующей
БД, прерывание до schema transaction и отмену connect; это не полная crash matrix.
Полный host create/model route ещё не подключён.

`sqlite_folder/creation` объединяет проверку проекта/полного пакета вложений,
резервирование выбранной пустой папки, CAS publication и SQL bootstrap. Блокирующая
публикация владеет lease сама: отмена async вызывающего не освобождает её во время
записи и не начинает SQL после утраты вызывающего. `Arc<PublishedCasBatch>`
удерживается VFS source до фактического close; после SQL ошибки известный UUID
не теряется при закрытии. Новые тесты проверяют чтение отдельным test process без
app index, отказ непустой папки и отмену на реальном барьере blocking job.
Это storage-fixtures со synthetic bytes, ещё не реальный CAD model commit.

Существующая запись теперь требует `ReadBinding`, который выпускает только
исходный FolderSession под mutex после проверки снимка. Он связывает opening,
расположение и исходный actual DB identity; VFS сравнивает с ним фактически
открытый writer base до разрешения journal/write. Одинаковые SQL UUID/seals копии
не заменяют физический источник. После начала собственного journal операция
может безопасно завершить transaction/rollback, даже если opening отозван;
результат нельзя принимать в закрытый UI-сеанс, а возможный COMMIT разрешается
по UUID. Close не обещает атомарно отменить уже начатый SQLite commit.

`FolderSession::commit` объединяет exact snapshot/history-intent checks, реальную
writer lease, CAS job и SQL commit. Исходный reader mutex удерживается до конца:
чтение этого сеанса не проверяет собственный journal как чужой recovery. После
COMMIT проверяются новый снимок и CAS; ошибка проверки, закрытия или отозванный
opening возвращается как Indeterminate с известным UUID, без replay.

Для долгой CAD-задачи `latest_compatible` допускает свежие metadata: те же
current revision/files/revisions, сохранённый исходный commit node и только
промежуточные commits с прежними cursor/archive seals. Один read transaction
проверяет полную валидированную цепочку без изменения схемы. Undo/redo или model
edit не становятся metadata-only после возврата геометрии. Результат — новый
exact snapshot для commit внутри прежнего opening.

Общая [подготовка modeling/command запроса](../integration/storage-model-request.md)
применена после отдельного разрешения на пять файлов. Она выделяет прежние
limits/program/ReviewPlan/no-op/job проверки без изменения порядка managed
permissions/tasks. Отдельно согласованный [общий orchestration-патч](../integration/storage-repository-apply.md)
применён: managed execution сохраняет исходный read session, сравнивает содержимое
ревизий/историю вместе с head/files и сохраняет совместимые последние metadata.
Pending recovery получает отказ вместо reconcile в этом маршруте. Folder adapter
теперь использует тот же алгоритм с отдельным task UUID открытия и явным
одноразовым Rust host grant. Разрешение сохраняет исходную opening/location
binding и не заменяет OS writer lease. Нужные STEP читаются из исходного снимка;
перед session commit проверяются совместимость исходных model/history и точное
последнее состояние. Неопределённый commit не превращается в успех. UI/IPC ещё
не подключены.

Native CI явно запускает ignored-тест `real_worker_folder_roundtrip` с переменной
`FORMA_FOLDER_TEST_WORKER`, указывающей на собранный worker. Тест создаёт пустой
самостоятельный проект, сохраняет коробки 40 и 80 мм через общий CAD execution,
делает undo к 40 мм, закрывает сеанс, проверяет сохранённый STEP отдельным
процессом с nonce-подтверждением, затем открывает папку и делает redo к 80 мм.
Настоящий worker проверяет объём и размеры. Workflow требует один выполненный
успешный тест; skips обычного library-запуска не доказывают этот маршрут.
Для новой вертикальной проверки ещё нужен успешный CI актуального head.

Доверенный backend `FolderSession::apply_history` использует существующий чистый
планировщик истории и настоящий session commit. Ему нужен захваченный снимок,
а не один revision ID. Новые синтетические проверки хранилища покрывают undo,
чтение CAS отдельным дочерним процессом, повторное открытие для redo и отказ
устаревшему/закрытому снимку. Они не доказывают корректность CAD-геометрии и
ещё требуют выполнения в CI.

На `1c5d59e` Linux library CI прошёл 387 тестов (9 ignored). Native-запуск
41326510425 прошёл 454 library-теста, 11 worker-тестов и host suites 7/7/9;
storage comparison и Clippy также прошли. Windows прервал процесс, когда тестовый
hook прочитал пустой заблокированный writer-lock файл. Теперь fixture проверяет
нулевую длину без чтения заблокированных байтов, а тестовые hooks перехватывают
panic до возврата через C ABI. Новые history-тесты и исправление Windows требуют
свежего CI.

Адаптер вложений folder executor заранее читает только выбранные захваченные
дескрипторы через проверенные session reads. Ограничения метаданных и суммарных
байтов уникальных хешей проверяются до выделения CAS-буферов; имена с одним хешем
используют общие сохранённые байты. Синхронный callback существующего CAD executor
принимает только выбранные дескрипторы и проверяет исходную opening/location
binding. Кэш входных данных не разрешает публикацию: после исполнения host обязан
повторно проверить исходную модель. Сам адаптер не запускает CAD и не подключает UI.

Независимый backend сохранения копии использует существующую пустую папку без
writer lease исходника и без строки app index. Он сохраняет revision IDs и
переносимую историю, назначая новые project/repository identity. Проверяет CAS
исходника, повторно проверяет исходный снимок после CAS staging назначения перед
SQL, затем ещё раз после публикации. Атомарной транзакции между двумя папками нет.
Если финальная проверка отказала после commit назначения, известный commit UUID
сохраняется в неопределённом исходе; автоматического повтора или удаления копии
нет. Прерванный staging может оставить невостребованные assets в папке назначения.
Байты и история исходника не меняются. Новые регрессии адаптера/копии требуют CI;
это backend API, ещё не доступные пользовательские сценарии.

Runtime CI 79431c2 выявил лишние отказы VFS: optional pager notifications SYNC и
COMMIT_PHASETWO ошибочно возвращали READONLY; теперь они сообщают NOTFOUND без
делегирования, как допускает SQLite. Bootstrap authorizer разрешает REINDEX
только для frozen main index при создании. Исходный recovery error сохраняется
через initial writer attestation. Эти исправления требуют нового runtime CI.

SQLite C ABI и платформенные bindings компилируются один раз для reader/writer;
дублирующие `#[path] mod` удалены после Clippy duplicate_mod/clashing extern errors.
Проверки на каждом IO используют identity/lease, а полный CAS hash — границы
публикации, чтобы не хешировать все вложения заново на каждой странице SQLite.

CI выявил, что соединение SQLx после ошибки COMMIT нельзя повторно использовать:
его закрывают, а outcome читают новым соединением. File-backed регрессия теперь
проверяет именно этот маршрут. На Windows каталог writer lease открывается с
FILE_LIST_DIRECTORY: attribute-only handle не обеспечивает требуемую проверку
delete sharing; прежний тест удержания assets обнаружил это ограничение.

Слой `sqlite_folder/session` сохраняет отдельное открытие и сериализует доступ
к его SQLite connection. Capture и повторная проверка сравнивают UUID источника
и проекта, коммит и проверенные хеши состояния. Close немедленно отзывает
открытие, включая ожидающие mutex операции. Снимок скопированной папки с теми же
UUID не принимается другим открытием. Чтение вложения требует точный дескриптор
из снимка, проверяет CAS и затем снова проверяет SQL-состояние. Новые регрессии
покрывают копию/переоткрытие, metadata commit при живом сеансе, close во время
ожидания и подмену вложения. Они также пока требуют исполнения в CI.
