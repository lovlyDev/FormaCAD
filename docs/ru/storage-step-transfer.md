# Перенос выбранного STEP в новый папочный проект

[Документация](index.md) · [English](../en/storage-step-transfer.md) · [Формат папки](storage-formats.md)

Это backend API этапа 4, пока только в тестовой сборке с native worker client.
Пользовательская кнопка и IPC ещё не подключены. Его назначение — взять явно
выбранный последний STEP и создать независимый FCP1-проект с настоящей проверенной
геометрией. Старая БД не ищется, не разбирается и не мигрирует. Старые credentials,
настройки, история и параметрическая модель не переносятся и не объявляются
восстановленными. Настоящий fixture проекта 1.1 пока не предоставлен; синтетическая
папка с реальным STEP не является доказательством полной совместимости 1.1.

## Действия host

1. После явного выбора файла host открывает `SelectedStep` и удерживает исходный
   `StepSnapshot`. Файл ограничен 40 МиБ; чтение проверяет identity, hash и lifecycle.
2. После явного решения создать проект host получает одноразовый
   `StepTransferGrant` для этого source opening и выбранной пустой папки. Grant
   непрозрачен, не сериализуется и не заменяет OS writer lease.
3. `step_transfer::transfer` принимает название, agent и prompt как новый intent,
   trusted CAD runtime paths и task services. Новый project UUID создаётся внутри.
   Единицы нового проекта — mm. База приложения и recent index не нужны.
4. Существующая `conversion::import_document::source` строит проверенный ImportStep
   CAD IR, содержащий hash выбранного asset. Затем общий `repository_apply::apply`
   выполняет подготовку, разрешение, очередь, отмену, настоящий `execution::build`
   и единственную подготовку `PreparedModelChange`.
5. До первой SQL-публикации worker должен успешно построить модель. Публикация
   добавляет исходный STEP к проверенным pending assets и использует существующий
   `creation::create_checked`. Первый commit содержит модель и новую историю
   импорта, а не пустой промежуточный project row.

## Проверки и исходы

Source opening/hash остаётся исходным через очередь, worker и публикацию.
Снимки копируют только Arc исходной capability, без повторного открытия пути и
без захвата нового hash. Назначение удерживает первоначальную location identity.
Перед SQL повторно проверяются источник и назначение, а после commit — точный
receipt, SQL/history и все CAS через общий publication verifier.

Ошибка до commit не объявляется сохранённой моделью. Отмена или отказ до staging
оставляют выбранную папку пустой; отказ после CAS staging может оставить только
собственные невостребованные assets для явного recovery. Ошибка после commit
возвращает `Indeterminate` с известным UUID: автоматического удаления или replay
нет. Лимиты FCP1 остаются прежними, включая 100 МиБ суммарных file references.
Старая папка получает только чтения выбранного файла.

## Воспроизведение

Unit-тесты проверяют закрытое/другое открытие, Send всей future, очередь/cancel,
непустую папку и невалидный intent. Это synthetic policy fixtures, не CAD.
Native workflow явно запускает ignored `real_worker_step_transfer_roundtrip` с
`FORMA_FOLDER_TEST_WORKER`. Он создаёт настоящий STEP коробки 40×20×10 через worker,
переносит его, проверяет первый commit и единственный ImportStep, перечитывает
геометрию/объём новым процессом и проверяет неизменность исходных файлов. Невалидный
STEP должен отказать до создания SQL/CAS назначения. Workflow требует один
выполненный PASS; отсутствие test match не считается успехом.

Новые тесты ещё требуют результата CI актуального head. USB/NAS, полный 1.1
fixture и production UI этим API не подтверждаются. Содержательные storage
workflows запускаются на push собственной ветки `codex/storage-week`, чтобы
конфликтующий PR при параллельных изменениях main не скрывал ошибки backend.
Они проверяют точный task SHA; чистая интеграция с текущим main и Quality остаются
отдельными обязательными gates перед передачей.
